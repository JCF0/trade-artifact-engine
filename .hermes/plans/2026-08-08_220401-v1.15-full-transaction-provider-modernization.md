# Artifact v1.15 Full-Transaction Provider Modernization Implementation Plan

> **For Hermes:** Implement only after explicit authorization, one review slice at a time. Do not commit, tag, push, call a live provider, or acquire fixtures unless separately authorized for that action.

**Goal:** Replace the production wallet-wide legacy Helius Enhanced-history enrichment path with a provider-neutral full-Solana-transaction path while preserving finalized standard-RPC completeness authority, all v1 wallet/candidate/package contracts, and exact established JUP/RAY identities.

**Architecture:** Keep finalized `getSignaturesForAddress` pagination, anchor construction, lower-bound proof, and latest-state recheck unchanged. Add a v2 internal provider port that pages finalized Helius `getTransactionsForAddress(transactionDetails: "full")`, validates and detaches each RPC transaction into a closed `solana_full_transaction_v1`, projects that representation into the existing `solana_spot_evidence_v1`, and then reuses the v1 classifier, normalizer, aggregate, candidate, selection, Slice 7, and package boundaries unchanged. An optional exact `getTransaction` fallback is missing-signature-only, explicitly budgeted, and never a completeness authority.

**Tech stack:** Node.js ESM, `node:test`, existing canonical JSON/SHA-256 helpers, existing injected HTTP/deadline/retry capability boundary, Solana JSON-RPC `json` encoding, Helius `getTransactionsForAddress`, standard `getTransaction`.

### 2.3 Fixed Helius requests

Bulk enrichment is a JSON-RPC POST to fixed `https://mainnet.helius-rpc.com/`, with the existing API-key query mechanism and no caller-supplied origin. Method and parameters:

- method: `getTransactionsForAddress`;
- address: requested wallet;
- `transactionDetails: "full"`;
- `sortOrder: "desc"`;
- `limit: 100`;
- `paginationToken`: omitted on first page, then copied opaquely from the prior result;
- `commitment: "finalized"`;
- `encoding: "json"`;
- `maxSupportedTransactionVersion: 0`;
- `minContextSlot: anchor_slot`;
- filters: `status: "any"`, `tokenAccounts: "none"`, and `slot: { lte: anchor_slot }`.

Do not set a lower-time filter: the canonical signature set is the target, and a server-side lower filter could hide a block-time contradiction rather than expose it during reconciliation.

Exact fallback is a JSON-RPC POST to the same fixed origin:

- method: `getTransaction`;
- parameters: `[signature, { commitment: "finalized", encoding: "json", maxSupportedTransactionVersion: 0 }]`.

No Wallet API, Parsed Events API, Enhanced endpoint, arbitrary RPC origin, `jsonParsed` parser dependency, ATA expansion, or transaction version greater than `0` is in scope.

## 3. Provider-neutral full-transaction boundary

Create `solana_full_transaction_v1` as a closed, canonical, provider-neutral representation. It is not an authoritative output and does not enter a hash directly; it is the validated input to the projector.

Required fields:

- version discriminator;
- signature, slot, block time, execution state, and transaction version (`legacy` or `0`);
- fee payer and explicit fee lamports;
- fully resolved account list in index order, including static and lookup-table addresses with signer/writable/source roles;
- pre/post lamport balances aligned exactly to the resolved account list;
- pre/post token-balance rows keyed by account index and carrying resolved account, mint, owner or explicit null, raw decimal string, decimals, and token program;
- top-level compiled instructions with deterministic outer index, program ID, resolved account addresses, and raw instruction data;
- inner-instruction groups bound to an outer instruction index, with the same normalized instruction shape;
- no description, provider source/type label, URL, header, API key, pagination token, JSON-RPC id, retry data, log prose, or unneeded response fields.

Validation requirements:

- generic unsafe-value detachment runs before structural classification;
- all Base58 identities use existing Solana identity validators;
- all integer quantities are safe nonnegative integers, except token raw amounts remain canonical decimal strings and lamport arithmetic uses `BigInt` internally;
- account/balance vector lengths and every account/program index reconcile exactly;
- loaded writable/readonly addresses are resolved deterministically;
- duplicate or contradictory token-balance rows fail;
- transaction signature is the first transaction signature and must equal the requested/canonical signature;
- null block time, absent meta, unsupported version, malformed instruction data, unsafe values, or mismatched arrays fail closed with fixed sanitized reasons;
- error detail is projected only to `succeeded`/`failed`; arbitrary provider error bodies do not survive.

## 4. Full-transaction projector design

Create a pure projector from `{ wallet, transaction: solana_full_transaction_v1 }` to the existing `solana_spot_evidence_v1`. Do not modify candidate or Slice 7 semantics to accommodate the provider.

Projection rules:

1. Build the union of pre/post wallet-owned token accounts by account index. Require stable mint, owner, decimals, and token program across both sides. Compute signed raw deltas exactly; zero net deltas are corroborating inventory, not economic legs.
2. Aggregate same-mint wallet deltas only through deterministic separately identified account legs so the existing classifier can prove RAY's two USDT debits aggregate to exactly 25,000.
3. Derive the analyzed wallet's native delta from exactly one resolved wallet system-account row. Require explicit fee and identify fee payer from the resolved message; sponsored/delegated transactions remain unsupported under existing rules.
4. Recognize Jupiter, Raydium, and Orca only from actual top-level/inner program IDs using the existing recognized-program allowlist. Provider labels and prose are unavailable and must remain non-authoritative.
5. Decode only the instruction families required by current semantics: SPL Token and Token-2022 `CloseAccount`, plus enough account binding to identify authority, closed account, and destination. Do not add a general program decoder.
6. Bind closure mint/owner from token-balance evidence, require the post-state disappearance/zero condition, reconcile the closed account's lamport decrease and destination increase, and subtract proven wallet-returned rent from native economics. External rent remains material and localizes only when one exact mint is known.
7. After fee and proven rent, map every nonzero wallet-owned native/token delta into one deterministic whole-transaction economic group only when one recognized spot program and one exact two-sided quote/base shape exist. Otherwise preserve complete operations and let the existing classifier return unsupported or ambiguous.
8. Unknown owner, conflicting rows, unmatched wallet-affecting instructions, impossible balance equations, or unbound closure effects become explicit unresolved effects; unknown-mint or quote-closure impact remains wallet-wide and fails result issuance exactly as v1.14.
9. Failed transactions preserve source identity/execution state and receive `failed_transaction`; do not fabricate committed economic effects.
10. Set provider classification code to `null`; extraction must not depend on legacy Enhanced `type` or `source`.

- null-token first request and null-token terminal completion;

- exact duplicate within/across pages accepted only after canonical-byte equality;

### Deadline and telemetry

- request timeout versus remaining overall deadline;
- abort-respecting rejection;
- abort-ignoring late success;
- synchronous timeout throw;

- retry count increments only immediately before an actual retry begins;
- timeout count increments once only when transport termination qualifies;

- exact explicit fee and zero fee;
- missing fee or wallet native row;

- Token and Token-2022 closure, wallet-returned rent, external destination, known/unknown mint, malformed/conflicting destination, missing post-state, duplicate closure, metadata-only/non-instruction closure;
- unresolved token-local versus wallet-wide impact and unchanged `wallet_wide_impact_unresolved` gate;

## 12. Review gates and stop conditions

Every slice stops when its focused tests pass and presents the diff plus new/changed authoritative assumptions. Do not carry a known failure into the next slice. Three classes are release-blocking:

1. Any inability to reproduce exact JUP/RAY normalized bytes, receipt hashes, package digests, or member hashes.
2. Any path that issues an acquisition result with missing, duplicated, contradictory, unbounded, late, or unreconciled provider evidence.
3. Any production path that retains raw live bodies, broadens capabilities, changes canonical completeness authority, or silently expands wallet/ATA scope.

Final release claims must say: “The system deterministically reconstructs supported results from provider-attested on-chain evidence and exposes the evidence boundaries and limitations required to reproduce its result.”
