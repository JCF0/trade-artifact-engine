# Artifact CLI/API read-only assessment

## Executive recommendation

**Split: preserve submission scope NOW; add a small offline library/CLI AFTER CONSTRUCT. Defer HTTP and general network verification.** There is useful implemented interface code, but no existing command is a drop-in public interface to the current source-authoritative v1.3 verifier. Reusing the historical mint CLI substantially unchanged would expose the wrong semantics and capabilities.

For Construct, prioritize the already-pending final reconstruction/release integration and its retained evidence. A terminal JSON inspector is optional: it materially helps only if a reviewer needs to independently inspect the exact released claim/evidence without project internals. If the demo merely shows the same result another way, it is another presentation surface, not a submission requirement. Do not make CLI work a new release gate. Existing historical proof pages can demonstrate historical artifacts, not substitute for the outstanding final-proof result.

The smallest eventual addition is an import-safe callable adapter plus one local, offline-only CLI, initially for integrity inspection and exact result retrieval. Source-bound replay is a separately qualified mode. An agent can consume these results without receiving a wallet key, economic authority, or permission to trade. Wiggles ingress remains a separate authenticated control plane.

## Minimal proposal — documentation only, not available commands

Proposed names and wrapper version below are interface sketches, **not existing files, commands or schemas**. Smallest first slice is `inspect` plus `result`; `verify` requires qualified retained-source replay; `acquire` is later work.

```text
artifact inspect --format receipt_package_v1 --input <package-dir> --expect-digest <package-digest> --json
artifact inspect --format artifact_immutable_semantic_claim_v1_3 --input <claim.json> --expect-digest <claim-artifact-digest> --json
artifact result --input <claim.json> --expect-digest <claim-artifact-digest> --json

# Later, offline source-bound replay; no automatic acquisition:
artifact verify --request <scope-and-selection.json> --evidence-root <frozen-root> --evidence-manifest-sha256 <sha256> --json
# Separately authorized later acquisition, never trading:
artifact acquire --request <bounded-acquisition-request.json> --evidence-out <new-private-root> --json
```

The callable equivalent should accept request data plus an explicit read-only evidence-reader capability, returning an object rather than printing. Avoid importing command modules. For position issuance, reuse the existing exact core request:

```json
{
  "candidate_population_digest": "<64 lowercase hex>",
  "requested_candidate_digest": "<64 lowercase hex>"
}
```

The adapter's separate request descriptor binds format/spec version, chain/network/genesis, analyzed wallet, exact window/finalized anchor where already known, target and exact quote mint, claim type/profile, expected input identities and evidence-manifest identity. No environment-selected wallet, latest-file discovery, prefix IDs or implicit candidate fallback. Acquisition uses the existing `wallet_wide_acquisition_request_v2` budget structure, not just a transaction cap; provider endpoint/credential capabilities belong to operator configuration, not arbitrary caller URLs. Validate supported scope before spending budget. A new anchor produces new evidence identity, not a reproducible replay of old bytes.

Illustrative wrapper response (angle-bracket strings are explanatory placeholders, not sample execution):

```json
{
  "interface_version": "artifact_verification_interface_v1",
  "operation": "verify",
  "validation_level": "source_bound",
  "input_identity": {"evidence_manifest_sha256": "<sha256>"},
  "result": "<unchanged current evaluation, selection result or immutable claim object>",
  "evidence_references": [{"path": "<safe relative member>", "sha256": "<sha256>"}],
  "error": null
}
```

`validation_level` is an adapter validation-depth label, **not an economic status**. Integrity inspection may expose a retained claim outcome as a field of the stored object but must explicitly say it has not source-revalidated that outcome. Missing admitted source material must never yield `source_bound` success.

Preserve `claim_outcome` exactly as **VERIFIED / LIMITED / BLOCKED / NOT_EVALUATED**, with independent **CLOSED / OPEN_REALIZED_PARTIAL / OPEN / null** position state, existing reason codes, exclusions, field availability and unresolved dependencies (`V/semantics.mjs:3-19,36-60`; evaluator `:523-560`). Do not collapse LIMITED to VERIFIED, unavailable values to zero, or claim-level verification to transaction/wallet/trader endorsement.

Proposed automation behavior:

- JSON mode emits exactly one versioned closed-schema object on stdout; diagnostics only on stderr. Pin canonical serialization and newline policy; no progress banners or timestamps in semantic identity.
- Exit **0**: requested operation completed, including a faithfully returned LIMITED/BLOCKED evaluation or selection refusal. Automation reads the existing outcome; process success is not economic success.
- Exit **2**: invalid request/unsupported format/identity or integrity mismatch; retain sanitized core error code in the wrapper error.
- Exit **3**: requested validation could not run because retained source dependencies are missing/unavailable. If the evaluator actually produced unresolved dependencies and LIMITED/BLOCKED, return that result under exit 0 instead.
- Exit **1**: operational failure, including filesystem/provider/timeout/budget errors. Do not manufacture a BLOCKED claim from an exception or imply retries are automatically authorized.
- A refused explicit selection returns its existing refusal object; no immutable claim is issued. Failed source-bound claim issuance stays a failure, not a synthetic lower-level substitute result.

If HTTP is later justified, keep this same contract behind a new isolated app: authenticate callers, authorize scope/budget and result ownership, use service-selected immutable roots/provider allowlists, bound body sizes/concurrency/time, deny caller paths/URLs, prevent cross-request caches and evidence disclosure, and sanitize logs. Valid evaluation results use HTTP 200 regardless of economic outcome; request rejection, missing prerequisites and service failures need documented distinct HTTP errors. Expensive acquisition may need durable jobs, cancellation and idempotency rather than synchronous handlers; that is extra work, not part of the minimal option.

What makes a “thin” wrapper grow: reconstructing non-serializable/private registered ports from retained bytes; proving boundary completeness and same-operation authority; repeated source recapture; safely preserving refusal evidence; unknown/symlink/oversized files; mixing old package and new semantic identities; evidence privacy/redaction; immutable publication/retrieval and crash recovery; arbitrary-wallet/route support; network retries, quotas and multi-tenant isolation. None is solved by a short command parser.

**Acceptance criteria for later implementation, not actions authorized here:**

1. Closed versioned request/response contracts; reject duplicate/unknown flags, malformed digests and ambiguous selections. Stable output bytes and exit classifications with hostile/truncated input tests.
2. Integrity-only and source-bound modes demonstrably distinct; fully rehashed but source-inconsistent claims rejected by source-bound replay. No caller-supplied outcome/economic authority.
3. Exact historical JUP/RAY receipt, package and member identities unchanged; current evaluator reason/outcome/state/availability vocabulary unchanged.
4. Import and offline invocation perform no network, credential lookup, key access, store mutation or listener startup. Inputs remain byte-identical; explicit roots and safe bounded reads only.
5. Optional acquisition separately authorized, budgeted and evidence-retaining; no budget resets during downstream reconstruction and no partial-history success promoted to completeness.
6. Focused interface tests plus separately authorized maintained acceptance and exact-source verification; this assessment's retained test counts do not substitute for that validation.
7. No general Artifact path reaches Wiggles signer/provisioning/submission. No live-enable flag or deployment change bundled with interface work.

**Submission-time scope:** this assessment only; finish already-required reconstruction/release/demo evidence independently. At most consider an optional offline result inspector after exact artifacts exist and only under a new bounded authorization. **Post-submission scope:** stable library contract and local CLI first, retained-source replay next, bounded acquisition when justified, HTTP only for a concrete remote-consumer need. The reusable public-project work is the contract, safe evidence loader, deterministic JSON/error mapping and boundary tests—not preservation of the old mint UX.
