# v1.8 Release Notes

## Summary

Artifact v1.8 adds safe same-mint multi-input swap normalization for deterministic local receipt generation.

The release handles a previously unsupported Jupiter shape where a wallet sends multiple token inputs of the same mint and decimals and receives exactly one wallet-side token output. It does not add general multi-hop, mixed-quote, native+token, LP, staking, transfer-cost-basis, USD normalization, or new board behavior.

## What v1.8 Adds

v1.8 adds:
- a shared deterministic same-mint multi-input aggregation helper
- runtime wiring through ingest, normalize, classifier, and run-pipeline paths
- deterministic parity coverage for the supported aggregation shape
- a no-network real-shape regression fixture based on the validated RAY transaction
- v1.8 regression runner
- v1.8 release, limitation, regression, and validation documentation

## Supported Shape

The aggregation path accepts only:
- multiple wallet-side token inputs with the same mint and decimals
- exactly one wallet-side token output transfer
- no simultaneous native input
- different input and output mints
- unambiguous ownership and direction
- no unexplained extra sent or received wallet-side assets

The helper sums integer raw input amounts first, then decimal-normalizes once.

## Real Validation

The validated RAY case was previously an `open_snapshot` / `unverified` outcome because the buy transaction was dropped by strict one-input / one-output normalization.

After v1.8 same-mint aggregation, the buy normalizes once as `events_swap_same_mint_aggregated`, the later sell consumes known inventory, and the resulting v1.2 receipt is:
- type: `closed_position`
- verification status: `verified`
- receipt hash: `4d33969c45a041837070dbc83730862325ff989772712aae285384d4570e4341`

The transfer-derived JUP negative control still fails closed.

## Compatibility Boundary

v1.8 may create new receipts from previously dropped events when local inventory is regenerated. It never rewrites stored receipts or changes existing canonical receipt hashes.

v1.8 does not change:
- canonical receipt schema
- verifier logic
- accounting rules
- ledger schema
- coverage statements
- board eligibility or ranking
- manifest selection
- upload, mint, signing, accounts, profiles, hosting, or deployment behavior
