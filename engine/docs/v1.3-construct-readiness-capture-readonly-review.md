No repository module, test, installation, RPC, credential lookup, wallet operation, signer, submission, Git mutation or delegation was executed. Only this report was written. Existing work and historical reports were preserved.

## Blocking findings

### RC1 — Timer delivery is substituted for the per-call deadline

**Locations:** `engine/src/verification-scope-v1-3/final-proof-agent/orca-readiness-capture-v1.mjs:89–119,141,303–307`.

Each RPC races transport against a timer. After transport wins, `remaining()` checks only the overall monotonic duration and absolute wall-clock deadline. There is no retained per-attempt monotonic deadline and no comparison against `call_timeout_ms` after settlement. A JavaScript timer is not an elapsed-time assertion: its callback can be delayed by the event loop.

**Reachable failure scenario:** configure the supported short per-call timeout and a longer overall timeout. A response callback becomes runnable before the timeout callback, but event-loop blocking delays both until after the per-call deadline. The response callback runs first; its promise/microtasks win the race. `remaining()` still sees time inside the overall budget, and `finally` clears the overdue timeout. The late response is retained, validated and used; with otherwise valid subsequent responses, capture can issue READY and authenticated composition can reach its signer callback. This needs neither a forged decision nor malicious administration. An abort-ignoring transport that completes synchronously after blocking past the call deadline exposes the same acceptance path.

There is a related overall-start gap: the monotonic start is taken **after** the initial awaited authority load (`:82–89`), while the outer timer is installed only after the work IIFE has begun (`:303–305`). Synchronous work in that first trusted callback is not charged to the monotonic capture duration. A callback that blocks before returning can consume the supposed overall budget before either enforcement mechanism starts measuring it.

Ordinary timer-fired failures do generally fail closed: when the outer timer actually fires, `expired` prevents final cache insertion; when the RPC timeout wins, there is no fee retry unless the error is the admitted provider code. That does not cover an overdue completion winning before the timer callback runs.

**Essential regression:** exercise the actual capture with an advancing monotonic clock and late settlement that wins the event-loop race, while the overall budget is still positive; assert refusal, no READY cache/manifest, and zero composed signer calls. Also charge an initial authority callback to the same absolute monotonic deadline. Include late success after abort/timeout and a later event-loop turn proving no further calls/readiness appear. The current hung-promise tests at `orca-readiness-capture-v1.test.mjs:157–163` and overall-clock mutation at `:130` do not cover these cases.

### RC2 — Cached freshness and the pre-sign guard discard monotonic age

**Locations:** `orca-readiness-capture-v1.mjs:70–74,279–299,309–316`; `orca-signing-composition-v1.mjs:75–80` (both under `engine/src/verification-scope-v1-3/final-proof-agent/`).

The cache retains only `{ source, challenge }`. Once capture completes, both build-input use and the immediate pre-sign freshness guard check `unixSeconds()` against the challenge expiry. They never read the monotonic clock, retain a monotonic expiry, reject wall-clock regression, or enforce a lower bound against issuance.

**Reachable failure scenario:** valid capture issues a short-lived challenge. During decision preparation or the durable signing checkpoint, wall time is corrected backward while monotonic elapsed time advances beyond the approved freshness interval. The wall-clock reading is still below challenge expiry, so cached build input and the pre-sign check succeed even though the observations are too old. Authenticated composition then invokes the signer callback. Durable one-time consumption does not repair stale source evidence. This is ordinary clock behavior, not the excluded administrator-database-restore threat.

The new guard is correctly placed after the durable ambiguity checkpoint, and wall-clock equality is rejected, but its clock basis is insufficient for the claimed maximum age at use.

**Essential regression:** after valid capture, advance monotonic time beyond freshness while wall time remains below expiry (including backward correction). Assert rejection at both cache access and the actual composed signing checkpoint, with zero signer calls. Retain the existing wall-clock equality tests. `orca-readiness-capture-v1.test.mjs:178–183,212–255` currently advances only wall time for these checks.

### RC3 — Real SDK decoding does not validate account discriminators or exact tick-array length

**Locations:** `engine/src/verification-scope-v1-3/final-proof-agent/orca-readiness-capture-v1.mjs:21–28,228–250`.

The pool and tick account owners and several decoded relationships are checked, but the code treats SDK decoding as account-type validation. The pinned SDK decoders do not provide that guarantee:

- `engine/orca-readiness-sdk/node_modules/@orca-so/whirlpools-client/dist/index.js:1822–1844` reads the pool discriminator as an arbitrary eight-byte field, not an asserted constant.
- The same pinned file at `:1253–1259` does the same for fixed ticks. `getTickArrayDecoder()` delegates to that fixed decoder at `:13426–13427`; its canonical size is 9988 at `:1294–1295`.
- `engine/orca-readiness-sdk/node_modules/@solana/codecs-core/dist/index.node.mjs:48–52` returns `decoder.read(...)[0]`, discarding the end cursor. It does not require complete input consumption.
- Capture supplies size 653 for pools but **no size** for tick arrays, and never checks either decoded discriminator. The quote facade accepts economic fields, not account discriminators (`whirlpools-core/dist/nodejs/orca_whirlpools_core_js_bindings.d.ts:701–704,748–757`).

These installed dependency bytes were compared with the integrity-verified cached tarballs identified by the manifested lock, rather than assumed authentic from their directory names.

**Reachable failure scenario:** a malformed raw route response keeps the mandated account owner, size, mint/vault relationships and quote fields but changes the pool's first eight bytes. Alternatively, change a fixed tick discriminator, or append bytes to an otherwise valid fixed tick payload. Base64 remains canonical and the existing checked fields remain unchanged. The SDK returns the same relevant fields; local checks and quote/message/fee binding do not reject the account-type or trailing-data defect. With the remaining valid synthetic responses, this path can reach READY and the composed signer callback.

This is a raw-provider validation failure, not evidence that the real frozen on-chain pool has changed type. A truthful chain execution may reject the resulting transaction; relying on that later rejection does not satisfy pre-sign route validation.

**Essential regression:** independently mutate the discriminator in the initial pool, the route pool, and a tick array; append a byte to a fixed tick array. Keep all other relationships and downstream fee correlation valid. Require failure before readiness/signing. Existing wrong-owner/mint/start-index probes at `orca-readiness-capture-v1.test.mjs:107–135` and retained positive decoding do not test this guarantee.

### RC4 — History exhaustion and repeated heads have no lower freshness binding

**Locations:** `engine/src/verification-scope-v1-3/final-proof-agent/orca-readiness-capture-v1.mjs:145–158,200–227`; `engine/src/wallet-acquisition/helius-rpc-validator.mjs:46–57`.

Opening account reads are explicitly floored to the finalized anchor, and owner enumeration is floored to opening. In contrast, every signature-history page and repeated head supplies only `commitment`, `limit` and optional `before`: **no `minContextSlot` or equivalent trusted freshness attestation**. Returned history has no response context. The checks `row.slot <= previousSlot` and `row.block_time <= anchor.block_time` impose upper bounds, not evidence that the history source has caught up to that anchor/opening. Two identical stale heads remain identical.

The installed pinned RPC API explicitly supports `minContextSlot` for this method (`engine/orca-readiness-sdk/node_modules/@solana/rpc-api/dist/types/getSignaturesForAddress.d.ts:20–46`). This observation is local API evidence, not a fresh external provider certification.

**Reachable failure scenario:** account/anchor calls reach an up-to-date backend, while all history requests reach an older finalized backend. After setup, recent finalized third-party token activity returns the token balances to their opening values, with transaction fees paid elsewhere; it completes before the controlled capture begins. Fresh opening balances and both owner lanes can therefore match. The lagged history backend returns complete old pages through an empty page, followed by the same old head. The old rows corroborate the setup timestamp; capture calculates eligibility from the fresh anchor against that stale history and issues READY despite the recent activity it promises to exclude.

This does not require activity *during* capture, an administrator restore, a false hash, or an on-chain atomic snapshot. It is precisely a cross-source freshness gap. Provider-attested completeness at an unbound older boundary is not completeness at the boundary used for eligibility. A minimum context remains only a freshness floor, not proof of atomic indexed history; the explicit provider-completeness and controlled-quiescence assumptions must still remain.

**Essential regression:** provide fresh anchor/opening evidence and a stale history source whose old nonempty pages terminate and repeat consistently. Assert the production requests demand the admitted floor on every page and repeated head, and that inability to satisfy it blocks readiness/signing. The current “incomplete history” empty-array test (`orca-readiness-capture-v1.test.mjs:125`) and single-page-cap test (`:169–170`) do not exercise stale-but-apparently-complete history.

## Assessment of the requested boundaries

### 1. Lossless metadata — PASS within the stated representation contract

`solana-rent-epoch-v1.mjs:3–19` admits safe nonnegative Number integers excluding negative zero, or canonical bounded decimal u64 strings. Numeric JSON rentEpoch validation uses `context.source`; unsafe-but-valid original integer tokens return their exact decimal source, not `String(unsafeNumber)` or `BigInt(unsafeNumber)`. Fraction/exponent spellings and unavailable numeric source context are refused. Direct unsafe Number adapter inputs remain refused.

Capture retains the raw response string before parsing (`orca-readiness-capture-v1.mjs:120–133`). The owner adapter's only production diff is importing the shared predicate and substituting the rentEpoch condition; its lamports/space/raw decoding remains in place. Normalized `rent_epoch: String(account.rentEpoch)` remains after validation (`helius-target-account-snapshot-adapter-v1.mjs:164–190`), and full-population hashing still includes normalized accounts (`:243–250`). Metadata is not dropped from identity.

The inspected tests explicitly distinguish original unsafe tokens, rounded Numbers and reserialized artifacts (`orca-rent-epoch-v1.test.mjs:6–51`); safe Number/string complete-result equality and changed-rent/different-identity are asserted in `helius-target-account-snapshot-adapter-v1.test.mjs:111–147`. Opening/enumeration disagreement remains refused. The unsupported-runtime test calls the reviver without source context; a historical pass on Node v22.23.1 is not evidence of a separately executed older-runtime matrix.

### 2. Source authority — correctly owned acquisition, subject to RC3/RC4

The factory takes trusted executor capabilities, not decision-supplied quotes/balances/history (`orca-readiness-capture-v1.mjs:46–67`). It requests raw evidence itself, hashes retained records, invokes the existing controlled enumeration authority, derives the SDK quote, constructs the message and obtains its fee. The trusted sink's matching hash acknowledges retention; it is not independent authentication of the provider or durable deployment.

Registered enumeration capture rejects an unbranded generic production-profile substitute (`target-account-enumeration-port-v1.mjs:473–505`). The final cache contains frozen locally derived source bound to an exact challenge. A caller-authored source hash is not accepted by the current capture path. Trustworthy transport wiring and actual durable sink implementation remain deployment prerequisites, not capabilities manufactured by these hashes.

### 3. Opening, completeness and age — substantive checks, but RC4 blocks full acceptance

Capture validates the exact system wallet and classic token envelopes, amounts, wallet authority, initialized/no-delegate/no-close-authority state, and the mandate balances. Mandatory owner validation inspects full populations before target filtering; capture additionally requires exactly the two expected classic accounts, no Token-2022 accounts, equal opening/owner watermarks, and account-evidence equality (`:157–199`). Equal watermarks are not represented as atomicity.

Each of three histories has a bounded page loop, explicit empty terminal page, nonempty observed history, no duplicate signatures within that history, descending slot bounds and repeated normalized head equality (`:200–223`). The strict age predicate derives from the finalized block time and the maximum observed setup-side history time, with mandatory corroboration of the frozen setup time (`:224–226`); it is not merely “wall clock reached the candidate” or an unchecked funding constant. However, RC4 means the observed population may be stale relative to that finalized block.

The manifest classification and controlled owner profile preserve provider-attested/non-atomic/third-party limitations (`:293–295`; owner adapter `:258–315`). This review does not demand an atomic standard-RPC primitive.

### 4. Route, quote and fee — strict slippage/fee binding PASS; account typing blocked by RC3

The implementation uses the actual pinned Whirlpool client and WASM quote engine, not caller-selected quotes. It derives directional tick PDAs, rechecks starts in the same route response, checks pool mints/vaults/classic fee-tier relation and decoded tick-to-pool relationships, and validates vault token authority. Absent ticks refuse rather than being synthesized empty (`:228–254`). RC3 concerns the additional account-type/encoding conditions those checks omit.

Strict minimum uses integer ceiling (`:255`), and the independent message boundary rejects any minimum failing the exact cross-product (`orca-message-boundary-v1.mjs:31–34`). The historical B1 defect is not reopened. Fee RPC receives the exact constructed message, its context is floored to blockhash context, fee must exactly match the mandate, and the resulting source binds `plan.message_sha256` (`:261–277`). Composition reconstructs the message and independently reconciles its fee hash (`orca-signing-composition-v1.mjs:34–45`). One admitted fee retry reuses identical message/parameters; no refresh/requote is present.

### 5. Disposal — source lineage retained; freshness limitations still apply

Capture reads quantity/evidence from reopened durable state and the first ordinal's retained signature, not request fields; fresh JUP, USDC and native balances must reconcile, and post-setup history permits only the retained successful acquisition signature (`:163–172,213–227`). It does not reapply zero-JUP opening.

The source-bound acquisition closure reconstructs the transaction/effects and exact acquired quantity (`acquisition-closure-authority-v1.mjs:78–145`); SQLite requires its branded proof, reconciles retained signed identity, rereads wire and atomically persists finalized evidence/quantity (`sqlite-decision-authority-v1.mjs:1010–1043`). Composition also compares durable disposal quantity and acquisition evidence (`orca-signing-composition-v1.mjs:28–43`). The new disposal capture positive is synthetic with injected authority, not a new end-to-end real acquisition closure. RC2/RC4 also affect disposal freshness.

### 6. Budgets and time — bounded attempts, incomplete elapsed-time guarantees

Explicit configuration is required. Aggregate attempts, per-method counts, response cap, history pages, per-call and overall timeout ceilings are enforced in capture. All nested owner calls pass through the same counters; owner-helper sleep rejects further pair retries. Only the single explicitly configured fee retry on code -32016 is admitted. No transport or provider retry policy is constructed here; an eventual real transport must not hide additional attempts.

Counters and explicit terminal pagination are useful controls. RC1 and RC2 nevertheless prevent an unqualified timeout/freshness PASS. Late work after an outer timer has actually set `expired` cannot populate the cache at the final guard; that narrower property is not proof of every late-settlement path. Existing tests never settle the hung promises and do not assert post-failure quiescence after a delayed completion.

### 7. Integration — immutable bindings and disabled live entry point preserved

The authenticated control plane validates principal/static bindings before durable decision lookups, loads the issued challenge from durable authority, and registers only a challenge matching current episode context (`wiggles-authenticated-control-plane-v1.mjs:135–172`). Composition keeps the prepared plan/challenge private, verifies source and exact fee-message commitments, consumes its pending plan even on failure, verifies the matching durable ambiguity checkpoint/revocation state, and invokes the capture freshness hook before its signer (`orca-signing-composition-v1.mjs:27–80`). Ordinary capture refusal prevents challenge issuance and the new refusal fixture asserts zero signer calls.

These identity and checkpoint checks do not establish truth/freshness of incorrectly admitted evidence; RC1–RC4 can precede otherwise valid authenticated composition. The optional hook preserves compatibility with earlier trusted source ports; it is not itself an untrusted caller bypass when this frozen capture object is wired as both ports.

`live-executor-composition-v1.mjs:9–14` still accepts no fields and unconditionally throws `bounded_agent_live_executor_not_released`. No production wallet/key/transport fallback was introduced.

## Later deployment gates — not current defects by their absence

The following remain separately required, and are not additional findings against this offline slice:

- real human/controller public identities, acquisition not-after, approved RPC-budget hash and final executor-release hash;
- reviewed production provider/transport configuration, retry behavior, freshness/completeness assurance, monotonic clock wiring and durable evidence sink;
- separate signer/runtime/administration identities, OS/key confinement, protected code/state, and supervised provisioning/stop/recovery procedures;
- authorized current-chain opening/eligibility/route/blockhash/fee evidence, then separately authorized signing and submission;
- exact retained-byte integration with the reviewed bounded scheduler, maximum three identical-byte sends, provider retries zero, no replacement construction, and terminal-evidence reconstruction;
- final reconstruction through the unchanged authoritative v1.3 economic pipeline and immutable claim gates.

The approved release remains **one supervised episode under trusted administration**, with ordinary crash durability but **without automatic administrator-snapshot rollback detection**. Known restore/reprovisioning/authority loss/ambiguous recovery still requires stopping. This review neither reopens the excluded detector nor treats synthetic proof fixtures as live final-proof evidence.

RC1–RC4 are current because they contradict implemented capture guarantees that the closeouts claim to have qualified. Resolving later identities or deploying an isolated signer would not cure them. No repairs, extra tests or further review cycle were begun. The review stops with this report.
