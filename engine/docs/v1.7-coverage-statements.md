# Artifact v1.7 Receipt Coverage Statements

## Scope

v1.7 Slice 1 adds deterministic Receipt Coverage Statements derived from existing local inventory, receipt, valuation, and verifier data.

Coverage statements are receipt-scoped. They do not describe a wallet, profile, account, portfolio, trader, full track record, skill, prize eligibility, or anti-wash-trading status.

## Contract

Coverage statements use:

```json
{
  "coverage_statement_version": "receipt_coverage_v1",
  "coverage_status": "complete",
  "coverage_codes": ["receipt_scope_only"],
  "scope": {
    "scope_type": "receipt",
    "coverage_basis": "canonical_inventory_receipt"
  },
  "receipt": {
    "receipt_hash": "<canonical v1.2 receipt hash>",
    "receipt_id": "<receipt id>",
    "receipt_type": "closed_position",
    "receipt_version": "1.2.0"
  },
  "position_episode": {
    "semantic": "closed_position_receipt_episode",
    "opened_at": 1700000000,
    "closed_at": 1700000300,
    "snapshot_at": null,
    "time_basis": "receipt_first_last_event_at",
    "descriptive_only": true
  },
  "verification_basis": {
    "verification_status": "verified",
    "hash_valid": true,
    "verifier_passed": true,
    "schema_valid": true,
    "consistency_valid": true,
    "rule_violations": []
  },
  "valuation_basis": {
    "valuation_status": "raw_quote",
    "valuation_currency": "raw_quote",
    "quote_symbol": "USDC",
    "quote_mint": "<quote mint>",
    "usd_normalized": false
  },
  "publication_context": null,
  "limitations": []
}
```

## Status And Codes

`coverage_status` is deterministic:
- `complete` when the receipt has confirmed hash, verifier pass, schema pass, consistency pass, raw-quote valuation, and existing event bounds.
- `incomplete` when one or more of those inputs is missing or not confirmed.

Missing `first_event_at` or `last_event_at` produces incomplete coverage with deterministic codes. It does not change board eligibility, ranking, count, links, canonical hashes, accounting, ledger behavior, or verifier behavior.

## Board Publication Context

The Historical Verified Receipt Board may attach:

```json
{
  "surface": "historical_receipt_board",
  "selection_mode": "publisher_selected"
}
```

This is publication context only. It does not prove population coverage or full inclusion.

## Boundaries

v1.7 Slice 1 does not add:
- HTTP routes.
- HTML rendering changes.
- Manifest fields.
- Ledger changes.
- Candidate generation changes.
- Canonical hash changes.
- Accounting changes.
- Normalization changes.
- Verifier changes.
- Same-mint multi-input swap aggregation.
- Upload, mint, signing, hosting, account, profile, or wallet permissions.
- USD normalization.
- PnL ranking.

Coverage statements must not expose wallet addresses, PnL amounts, USD amounts, normalized valuation, participant totals, profiles, Nansen labels, upload fields, mint fields, signing fields, or transaction-signature fields.

## Slice 2 JSON Exposure

v1.7 Slice 2 exposes the same reusable core `coverage_statement` on:
- `GET /api/proof/:receiptHash`
- `GET /api/verifier/:receiptHash`

These surfaces do not pass publication context, so `publication_context` remains `null`. The Historical Verified Receipt Board remains the only current surface that adds board publication context.

For the same inventory record, proof-detail and verifier coverage statements must deep-equal. This preserves the statement as reusable receipt-scoped metadata rather than a surface-specific interpretation.

## Trust Boundary

Proof-detail trust output may report `coverage_statement_present: true` because the JSON response includes a `coverage_statement`. This presence flag must not increase proof strength by itself.

The existing trust level remains derived from receipt identity, hash validity, verifier status, and source anchors. Slice 2 does not promote a receipt to `coverage_scoped`, does not alter `current_level`, and does not change verifier logic.

## Slice 3 Human-Readable Displays

v1.7 Slice 3 adds compact human-readable coverage displays to:
- proof-card JSON as `coverage_summary`
- proof-card HTML preview
- receipt-board HTML preview

The proof-card summary is derived only from the existing `coverage_statement`. It does not recompute scope from wallet, ledger, inventory, or verifier internals.

The receipt-board preview renders each row's existing `coverage_statement` and does not change board JSON, ranking, eligibility, count, links, hashes, or route behavior.

Required compact wording:
- `Coverage Statement`
- `Receipt-scoped coverage only.`
- `Receipt event bounds: <opened ISO> to <closed ISO>.`
- `Receipt event bounds incomplete.`
- `Raw quote only. No USD normalization.`
- `Not wallet, trader, portfolio, or track-record coverage.`
- `Publisher-selected board entry.` for board rows with publisher-selected publication context

Deferred surfaces:
- gallery
- new coverage routes

Slice 3 does not display wallet addresses, PnL or USD amounts, coverage codes, verifier diagnostics, upload fields, mint fields, or signing fields in the compact coverage display.

## Slice 4 Static And Hosted Proof Displays

v1.7 Slice 4 exposes the compact human-readable coverage display on static proof export and hosted proof-preview HTML through `renderStaticProofPage`.

The display is derived only from `proofDetail.coverage_statement` and is inserted after `Receipt` and before `Verification`.

Required wording:
- `Coverage Statement`
- `Receipt-scoped coverage only.`
- `Receipt event bounds: <opened ISO> to <closed ISO>.`
- `Receipt event bounds incomplete.`
- `Raw quote only. No USD normalization.`
- `Not wallet, trader, portfolio, or track-record coverage.`

Publisher-selected wording remains board-only and is not shown on static proof export or hosted proof-preview pages.

Slice 4 does not alter routes, trust strength, proof bundle structure, `proof.json`, hashes, verifier logic, manifest behavior, ledger behavior, accounting, normalization, upload behavior, mint behavior, or gallery tiles.
