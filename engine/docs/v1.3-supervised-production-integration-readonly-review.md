## 2. Blocking findings

### B1 — The source adapter silently requires setup to be older than 30 days, not the approved strict seven-day boundary

**Severity: high — an otherwise eligible acquisition can sign/finalize but cannot obtain its required source closure/disposal authority.**

The rehearsal contract requires strict seven-day age at the original opening, with earliest candidate `1789216029` (`D/v1.3-supervised-deployment-rehearsal-pack.md:218–236`; supervised checklist:59–62). The source adapter fixes a 30-day lookback (`A/supervised-finalized-source-v1.mjs:68,106–113`), places every in-window row into the economic transaction set (`:77–81,97–100`), and dispatches to v3 admission (`:116`). Admission then unconditionally requires `oldest > latest_setup_block_time` (`A/supervised-history-v1.mjs:21–25`). Subtraction is the actual boundary implementation (`W/boundary-contract.mjs:23–29`).

For the recorded setup time `1788611228`, the 30-day oldest timestamp at the seven-day candidate is `1786624029`, so that predicate is false. The first timestamp satisfying this extra exclusion is `1791203229`, not the approved seven-day candidate. These arithmetic values were calculated locally, not inferred from a live clock or chain.

**Reachable scenario:** approved configuration and fresh readiness at an eligible opening between seven and thirty days after setup; acquisition executes successfully; `finalizeRetainedIntentV1(1)` invokes the source adapter via `A/wiggles-trusted-runtime-v1.mjs:178–181` and `A/wiggles-submission-v1.mjs:488–511`. Original setup rows are still in the fixed 30-day history. Non-swap setup bodies can first fail the swap-only source decoder (`A/final-episode-release-v1.mjs:64–78`); even bodies reaching admission encounter the unconditional age failure. Acquisition closure cannot commit, disposal cannot be issued, and the economic-source phase was already consumed (`A/supervised-finalized-source-v1.mjs:34`). This is an implementation mismatch, not missing real provider evidence.

The required correction is not an unchecked narrowed history, invented window or silent extension of the authorized age. The complete admitted history and required setup bodies must remain independently accounted for while supporting the original eligible interval.

**Essential missing regression:** composed producer → acquisition closure → exporter/replay with original setup inside the 30-day window but strictly outside the seven-day opening boundary, including equality cases and distinct address-specific setup rows. Current positive integration uses wall time `1900000010` (`A/fixtures/trusted-runtime-offline-v1.mjs:9`), far beyond this interval. Existing v3 tests deliberately put the setup sentinel outside the economic window (`A/supervised-history-v1.test.mjs:11–47`) and do not demonstrate this required case.

### B2 — New economic-source and simulation RPC effects do not inherit the runtime deadline at the actual dispatch boundary

**Severity: high — reads may start outside the configured execution window. This finding does not assert late signing or extra sends.**

The common runtime deadline is validated during construction (`A/wiggles-trusted-runtime-v1.mjs:140–142`), but runtime `now()` only checks `closed` and returns a wall clock (`:217`). `captureRetainedOutcomeSourceV1` therefore remains callable after that deadline (`:244–254`). Successful finalization also reaches source capture without a current runtime-deadline check (`A/wiggles-submission-v1.mjs:488–511`).

`A/supervised-finalized-source-v1.mjs:33–36` constructs the new RPC wrapper with phase budget/clock but no absolute runtime deadline. The wrapper uses its own lazily started monotonic interval (`A/supervised-rpc-v1.mjs:25–44`). After durable request retention it checks only abort and that local interval, then invokes transport (`:58–60`). Consequently a runtime opened before its deadline can start economic reads after expiry, or cross expiry during phase/journal persistence and still dispatch. The relative phase timer is not the administrator's absolute window.

Simulation has a related effect-boundary gap: freshness is checked before entering RPC and after its response (`A/supervised-simulation-v1.mjs:16–21,35–45`), but not after the RPC's durable request write immediately before the real callback. A challenge can have only a small amount of time remaining while its phase call budget is larger; a durable write crossing challenge/runtime expiry but not the local call timeout still permits `simulateTransaction`. Later freshness rejection prevents wallet signing, but cannot undo that unauthorized late read.

**Essential missing regressions:** zero economic transport calls when an already-open runtime's deadline has elapsed; crossing the deadline inside phase consumption or request fsync; simulation crossing challenge/runtime expiry in request retention while still inside the relative RPC timeout. Assert actual transport counts and durable phase consumption, not merely a later rejection. Existing `A/supervised-rpc-v1.test.mjs:12–29` tests raw retention, method/call limits and late transport settlement; `A/supervised-simulation-v1.test.mjs:31–36` tests stale completion. Neither supplies these runtime/dispatch cases. The repaired submission boundary already demonstrates the needed distinction (`A/wiggles-submission-v1.mjs:420–437`; timing tests), and is not being reopened as a defect here.

### B3 — Retained revocation is not reconciled across the durable authority, journal and exported control record

**Severity: high — omission can change a revoked outcome into authenticated/unrevoked output; the demonstration gate depends on that output.**

There are two related reachable paths:

1. **Ordinary interrupted retention:** the supervisor commits revocation through the control plane, then separately appends the full revocation bytes/result (`A/wiggles-trusted-runtime-v1.mjs:233–236`). If the process stops after durable revocation but before that append, the authority remains revoked. Export reads that authority (`A/supervised-exporter-v1.mjs:69`) but does not reconcile its `revoked`/`revocation` identity with journal revocation records. It emits `revocation: null` when the journal lacks the wrapper record (`:107–113`). A normal journal head can remain intact in this window. The exporter must not infer no revocation from absent wrapper output when its own durable input says otherwise. Missing authenticated bytes should remain missing evidence, not an unrevoked conclusion.
2. **Rehashed contradiction:** take a genuinely revoked operational package retaining its authenticated revocation in the journal; replace only `control.revocation` with null and refresh the outer package inventory. `A/retained-supervision-v1.mjs:11–67` verifies journal linkage and economic sources but never reconciles a `kind: 'revocation'` entry with `control.revocation`. Simulation and projection validation also do not make that comparison (`:101–132`). `A/retained-final-control-v1.mjs:123–128,233–237` applies and reports revocation solely from the nullable control field. It can therefore report authenticated, NOT_RETAINED/unrevoked control despite a contradictory authenticated revocation still present in the same admitted package.

For the already-covered revoked-after-acquisition outcome, this changes the reported outcome back to acquisition-closed/unrevoked. A disposal can also be revoked after submission while its escaped transaction later finalizes: this is an explicitly supported state-machine path (`A/episode-state-machine-v1.mjs:211–215,220–224`; durable authority `A/sqlite-decision-authority-v1.mjs:887–916,1047–1068`). If both legs' transmission/economics otherwise reconcile, omission of revocation removes the distinction on which `A/final-episode-release-v1.mjs:190–197` relies to deny demonstration success. This is a static reachable scenario, not a claimed executed tamper result.

Hashes need not prove provider truth to reject this contradiction: the original revocation evidence or the exporter's durable revocation identity is already available. This finding does not require defending against an administrator fabricating an entirely consistent replacement history.

**Essential missing regressions:** interrupted wrapper retention after committed revocation, then existing-state reopen/export; fully rehashed `control.revocation = null` while preserving the journal record; revoked in-flight disposal followed by retained finality. Require accurate revoked/unknown evidence classification and no successful demonstration. Current exporter test revokes once after acquisition and only tests the untampered result (`A/supervised-exporter-v1.test.mjs:34–82`); its complete-export tamper table does not cover revocation (`:173–190`).

### B4 — Export selects the first authenticated request, not the request actually admitted to the durable ordinal

**Severity: medium — a rejected request can permanently prevent export of a subsequent valid episode.**

Authentication and configured-principal checks correctly precede durable lookup (`A/wiggles-authenticated-control-plane-v1.mjs:157–169`). However, the observer stores the request before complete challenge/admission validation (`:171–175`). A configured agent can send a canonically signed request naming the issued challenge but containing a different well-formed nonce or predecessor digest. Context-free signature validation accepts its shape/signature (`A/agent-decision-v1.mjs:43–53`); the later contextual check rejects the mismatch (`:54–67`). This rejection occurs before ordinal consumption (`A/offline-executor-core-v1.mjs:95–112`). A corrected valid decision can still be admitted using that original unused challenge.

The exporter gathers all such requests and unconditionally uses `attempts[0]` for each challenge ordinal (`A/supervised-exporter-v1.mjs:70–80`). It reruns admission on that rejected first request, throwing before it can use the later successfully consumed decision. For signed legs the later admission-digest comparison (`:85–86`) does not rescue this ordering; the first request has already failed. Retaining rejected evidence is appropriate; treating its array position as the authoritative admitted request is not.

**Essential missing regression:** configured-principal, validly signed but challenge-context-invalid request, followed by a valid request before expiry, completed retained outcome and operational export. Require original rejected evidence preserved and control membership selected by the durable decision/challenge/admission identity (`A/sqlite-decision-authority-v1.mjs:1094–1100`), without granting replacement signing. Existing capability-injection and wrong-signature tests do not exercise this exporter sequence.

### B5 — Idempotent revocation replay makes an otherwise exportable revoked episode unexportable

**Severity: medium — lost-result reconciliation breaks the evidence handoff.**

Exact authenticated revocation replay deliberately returns `ALREADY_REVOKED`, including after restart (`A/wiggles-authenticated-control-plane-v1.mjs:219–232`). The integrated wrapper appends a journal `revocation` record for every successful return, including that replay (`A/wiggles-trusted-runtime-v1.mjs:233–236`). The exporter rejects any journal containing more than one such record (`A/supervised-exporter-v1.mjs:107–108`).

**Reachable scenario:** revoke after acquisition, lose the response, reopen and resend exactly the same bytes. Durable revocation succeeds idempotently and no extra execution authority is obtained, but the journal now contains two valid deliveries of one revocation and export throws `SUPERVISED_EXPORT_INVALID`. This is not contradictory revocation and must not require deleting preserved records to produce the outcome package.

**Essential missing regression:** exact revocation delivery → reopen → exact replay → operational export → fresh-process reconstruction. Preserve both delivery records, bind them to the single durable revocation, and keep the revoked outcome. Existing control-plane replay coverage establishes the lower layer; the integrated exporter test uses only one delivery.

### B6 — An unselected export prevents the later selected derived package for the same source ordinal

**Severity: medium — the prescribed inspect-then-select retained-package workflow is incomplete.**

The rehearsal requires preserving an unselected package and creating a new derived package identity when explicit selection is later supplied (`D/v1.3-supervised-deployment-rehearsal-pack.md:186–188`; reconstruction completion:116–118). The runtime permits null or digest-bound selection (`A/wiggles-trusted-runtime-v1.mjs:259–262`; exporter `:53–60`) but fixes every output for a source ordinal to `retained-export-${ordinal}` and performs an exclusive directory creation (`A/supervised-exporter-v1.mjs:119–121`).

**Reachable scenario:** export ordinal 2 with null selection, independently inspect/reconstruct its complete population, then request the selected derived package for ordinal 2. The second export fails because the destination already exists. No API parameter provides another private child identity; deleting or editing the first package violates preservation. Calling `inspectRetainedExportCandidatesV1` before the first export is a useful alternate path, but does not implement the documented preserved-unselected → selected-derived workflow.

**Essential missing regression:** two exports for the same source, first unselected and then explicitly selected, with distinct exclusive private destinations and byte-identical original evidence. Existing complete-export coverage selects before its only export (`A/supervised-exporter-v1.test.mjs:162–169`). This is a small private exporter requirement, not deferred CLI/API work.
