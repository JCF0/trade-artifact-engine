## Exact repair and input contract

New `engine/src/wallet-acquisition/solana-rent-epoch-v1.mjs` provides:

- A predicate accepting nonnegative safe Number integers, excluding negative zero, or canonical unsigned decimal strings in `[0, 18446744073709551615]`.
- A JSON.parse reviver that validates numeric rentEpoch against the original `context.source` token. Safe numeric tokens retain Number representation; unsafe but valid exact u64 tokens become their original decimal strings. Fraction/exponent numeric spellings are not part of this wire-token contract, even if Number would round them to an integer. String values must satisfy the same canonical decimal/range rule.
- A runtime lacking JSON source-token support fails closed for numeric rentEpoch. Verification used Node **v22.23.1**, the existing runtime; no runtime installation was performed.

The owner adapter now uses this predicate instead of its safe-Number-only rentEpoch condition. Its existing output remains `rent_epoch: String(account.rentEpoch)`, applied only after validation. Capture reuses the same predicate and reviver rather than maintaining a second permissive string rule. Its pre-existing rejection of unsafe non-rent numeric fields remains intact.

No general balance, amount, context or JSON numeric coercion was added. The shared adapter still takes parsed transport data: callers must preserve exact input before invoking it. Passing an unsafe Number still fails; the adapter does not try to repair a caller's lost information. The readiness capture and retained replay are the lossless parsing call sites exercised here. Unrelated live/probe runners were not changed or executed.
