# Wiggles trusted runtime — focused read-only review

## Verdict

**BLOCKED: two concrete exception-path defects in the new runtime adapter.** The authenticated decision boundary, one-time signing checkpoints, exact-message binding and disabled intended live launch remain intact in the inspected source. The blockers below concern the new adapter's claimed durable readiness-evidence retention and mutable key-buffer cleanup; neither is a demonstrated unauthorized-signing or replacement-signing bypass.

This is one static, read-only review of the retained acceptance snapshot, not a fresh test execution or host-deployment certification. Only this report was written. No tests, application imports/execution, installation, live RPC, credential/key-file access, signing, infrastructure changes, Git mutations, delegation, repairs or second review cycle were performed. Published disposable fixture source was inspected, not executed.

Scope remains supervised execution with a trusted administrator. Automatic detection of an administrator-restored internally valid snapshot is excluded and is not reopened here. Existing capture/rentEpoch repairs were inspected only at the new dispatch, freshness and evidence-sink integration boundaries.

## Blocking findings

### B1 — Existing readiness evidence can be accepted without establishing file-data durability

**Location:** `engine/src/verification-scope-v1-3/final-proof-agent/wiggles-trusted-runtime-v1.mjs:78-104`, especially 84-96 and 97-103.

`retainEvidence` fsyncs the evidence file only when its exclusive create succeeds. On `EEXIST`, it skips the file descriptor/write/fsync block, fsyncs the directory and compares readable file bytes through `privateBytes`. That helper does not fsync the existing file. Directory fsync and successful page-cache readback do not establish that an existing file's contents were durably flushed.

**Reachable scenario:** a capture writes a complete content-addressed raw response, then its file fsync throws. The function closes the descriptor and propagates failure but leaves the complete file behind. No decision has yet been consumed, so another supervisor capture is permitted. If it encounters the same record, `EEXIST` selects the no-file-fsync branch and returns its digest as retained evidence. This is directly possible with the released synthetic transport/clock: its fixed wall/monotonic values and identical genesis response produce the same first raw record on another acquisition capture (`fixtures/trusted-runtime-offline-v1.mjs:9-14,25-31`; `orca-readiness-capture-v1.mjs:149-155,173-175`). It also matters for any equal record left by interrupted/concurrent capture.

A later capture can finish, durably register a challenge and proceed to signing while one referenced raw record has no successful file-data durability operation. A subsequent storage/power-loss event can lose that raw evidence despite the accepted challenge and signed intent. This contradicts the new fsync-backed evidence-sink contract in `engine/docs/v1.3-wiggles-trusted-runtime-deployment.md:14` and the closeout's retention guarantees.

The first failed capture itself does not grant readiness. The problem is the later reuse of its unproven file. This is not administrator rollback or a broad capture-algorithm finding, and it does not establish a defect in the separate signed-wire fsync path.

**Essential regression:** through the real runtime and disposable synthetic transport, inject a one-time evidence-file fsync failure after the complete first raw-record write. Repeat capture with an identical record and require either fail-closed refusal or a successful fsync of the verified existing file before its digest is accepted. Also cover an existing-file fsync failure, byte mismatch and a complete file left by interruption. Observe file versus directory descriptors separately; a directory-fsync count alone is insufficient.

### B2 — Key-read exceptions bypass cleanup of the allocated secret-bearing Buffer

**Location:** `engine/src/verification-scope-v1-3/final-proof-agent/wiggles-trusted-runtime-v1.mjs:23-44,52-55,68-75`.

The local `bytes` Buffer is allocated inside `privateBytes` at line 31. Only explicit short-read and metadata-mismatch branches clear it. Its `finally` closes the descriptor but does not clear the allocation on other exceptional exits. The outer signer's `bytes = privateBytes(...)` assignment occurs only after the helper returns successfully.

**Reachable scenario:** after a successful partial/full wallet read, a subsequent `readSync`, post-read `fstatSync`/`lstatSync`, or `closeSync` throws an ordinary I/O error. The helper exits without returning its Buffer; the outer `bytes` variable remains undefined, so the signer's `finally` cannot wipe it. An exception from `closeSync` can similarly cancel the pending return of a fully populated Buffer. The allocated bytes remain unwiped until garbage collection/reuse.

Signing fails closed and the consumed `KEY_LOAD_STARTED_AMBIGUOUS` checkpoint remains; this finding does not claim a successful channel response, leaked channel contents or renewed signing permission. It does invalidate the explicit guarantee to clear retained mutable key byte arrays on failure (`engine/docs/v1.3-wiggles-trusted-runtime-deployment.md:17`; closeout:64). This is an application-owned mutable Buffer, not one of the expressly excluded immutable JSON strings, VM copies or crypto-internal allocations. Host isolation still matters; no cross-UID memory disclosure was demonstrated.

**Essential regression:** observe the actual Buffer passed to the real key-file `readSync`, populate a disposable-key prefix, then inject a subsequent read failure, post-read metadata failure and descriptor-close failure independently. Require that exact allocation to be zeroed on rejection, zero cryptographic signing, no successful intent, and preserved consumption across reopen. Existing `wiggles-trusted-runtime-v1.test.mjs:24-54,128-157` observes arrays passed to `nacl.sign.detached`, not a helper-owned allocation that never reaches signing; its cleanup assertion is vacuous when that observation list is empty.

Both findings are source-traced exception scenarios, not executed fault reproductions. No prohibited regression or key operation was run to confirm them dynamically.

## Reviewed guarantees and reachability

### 1. Authenticated ingress

- `wiggles-decision-channel-v1.mjs:6-35` accepts one bounded byte envelope through trusted supervisor-supplied streams and forwards only those bytes. It does not interpret a signer, path, operation selector, time, quantity, state or transaction supplied by the controller.
- `wiggles-trusted-runtime-v1.mjs:106-153` freezes and validates trusted configuration before opening existing authority. The agent surface at 157-161 has only `submitDecisionBytesV1`; readiness/revocation and retained-wire readback are separate supervisor/trusted surfaces at 162-170.
- `wiggles-authenticated-control-plane-v1.mjs:155-172` canonical-parses, verifies the decision signature and checks its configured agent/episode/mandate/authorization/release bindings **before** loading state or challenge. `agent-decision-v1.mjs:43-68` supplies closed-schema signature and complete-context checks. Durable state and registered challenge, not controller assertions, determine admission.
- Alternate exports were traced: generic offline core/composition and provisioning APIs still require trusted in-process capabilities; none exports or retrieves the new private JSON-key signer. They are not host-security boundaries. The launch contract must prevent Hermes from supplying code or running as the runtime UID. No alternate production launch of the new adapter was found in the inspected usages/package scripts.

### 2. Key loading and exact signing

- Human signature and configured static bindings are checked in `human-authorization-v1.mjs:45-70`; admission/time/state reconciliation is in `executor-admission-v1.mjs:62-86` and `episode-state-machine-v1.mjs:136-173`.
- `offline-executor-core-v1.mjs:95-138` requires atomic consumption, prepares the message and awaits PREPARED and KEY_LOAD_STARTED_AMBIGUOUS before invoking the signer. SQLite revocation and consumption serialize through `BEGIN IMMEDIATE` transactions (`sqlite-decision-authority-v1.mjs:631-640,785-847,939-940`).
- `orca-signing-composition-v1.mjs:61-83` consumes its private plan even on failure, verifies the exact durable checkpoint and checks cached freshness before key access. The new adapter rechecks revocation/checkpoint and the same freshness capability after actual key IO/derivation (`wiggles-trusted-runtime-v1.mjs:143-150,64-65`).
- Wallet access is confined to the configured path, with no-follow, owner/mode/size/single-link checks. The 64-byte key is checked against its derived public half and expected wallet; the canonical one-signer message must name that wallet (`wiggles-trusted-runtime-v1.mjs:23-67`). B2 qualifies its cleanup claim.
- Exact Orca construction remains private-plan-bound, including challenge/source and exact fee-message hashes (`orca-signing-composition-v1.mjs:27-57`; `orca-message-boundary-v1.mjs:19-81`). No new bypass of the repaired capture freshness checks or rentEpoch handling was identified.

Revocation after key-load start is an ambiguity/reconciliation case, not a guarantee of atomic cancellation of an already-started signing operation. The post-load check is useful but is not a transaction spanning cryptographic execution across processes.

### 3. Durable success and release

- `orca-signed-wire-boundary-v1.mjs:16-64` verifies the exact message and signature, exclusively creates the wire file, fsyncs file and directory, and rereads the bytes.
- `wiggles-authenticated-control-plane-v1.mjs:91-110` awaits independent authority read/parse/cryptographic verification and SIGNED_INTENT_DURABLE registration. `sqlite-decision-authority-v1.mjs:421-471,942-985` binds the retained message hash, wire hash and signature to the reserved identity and handles signed-after-revocation conservatively.
- The typed episode-state transition must also complete before the outer decision call returns (`wiggles-authenticated-control-plane-v1.mjs:122-133,173-177`). The runtime returns only status, episode ID and intent digest. Channel failures return NOT_SUCCESSFUL with SUPERVISOR_RECONCILIATION_ONLY_NO_REPLACEMENT, not an assertion of non-consumption or non-signing.
- `sqlite-decision-authority-v1.mjs:1115-1127` selects retained bytes by episode/ordinal and reruns the complete verifier. Trusted readback is deliberately available for reconciliation and is **not** submission permission; it must never be treated as such by a future executor. B1 concerns readiness evidence, not this wire verifier.

### 4. Concurrency, exceptions and restart

Existing runtime open refuses absent authority and validates the existing schema/rows in one startup read transaction (`sqlite-decision-authority-v1.mjs:474-607`). There is no runtime provisioning/reconstruction fallback. Consumption atomically updates ordinal and episode state; exact replay is distinguished from conflicting identity reuse (785-847). Private pending plans are deleted before signing attempts, and reopened capture starts with no cached readiness (`orca-signing-composition-v1.mjs:62-65`; `orca-readiness-capture-v1.mjs:68,87-96`). No consumed/ambiguous path was found that regains permission through ordinary reopen or duplicate decisions.

The positive runtime tests exercise ordinary close/reopen and two instances in one process (`wiggles-trusted-runtime-v1.test.mjs:94-117,171-187`). They do not prove new cross-process runtime composition or runtime-level crash behavior. The retained suite includes real underlying-authority cross-process consumption and post-commit SIGKILL tests (`sqlite-decision-authority-v1.test.mjs:250-310` and subsequent checkpoint/revocation cases), plus authenticated-control-plane race tests at 749-805. Those support the reused checkpoints, not the new helper's untested filesystem exception branches.

### 5. Test/production separation

The positive test at `wiggles-trusted-runtime-v1.test.mjs:71-117` creates a disposable key file, constructs the real new runtime, uses its real capture and private JSON-key adapter through the pipe handler, and rereads durable wire after reopening. It is not an injected inert signer positive test.

`executor-mandate-profile-v1.mjs:37-64` confines its alternate domain to fixed disposable wallet/ATA/control identities and dispatches other profiles to the unchanged strict validator. The executable runtime explicitly requires that offline profile at `wiggles-trusted-runtime-v1.mjs:129-131`. Production preflight calls the strict final-proof validator first and rejects published test identities/placeholders (`wiggles-production-configuration-v1.mjs:11-26`). Tests at `wiggles-production-configuration-v1.test.mjs:40-45` explicitly show a structurally valid production configuration cannot enter the offline runtime. Generated structural test principals prove consistency, not real principal ownership or approval.

### 6. Deployment and release boundary

The proposed separate controller/runtime/administrator identities, private directories, administrator-owned immutable source/dependencies, clean environment and restricted descriptors can support the stated separation **if actually implemented and verified**. The example at `engine/deployment/wiggles-supervised-v1.example.mjs:3-26` is declarative, intentionally incomplete and not installed/consumed. Names, umask strings and API partitions do not enforce UID, group, ptrace, `/proc`, descriptor or filesystem confinement by themselves. The documentation accurately leaves those host properties unverified (`engine/docs/v1.3-wiggles-trusted-runtime-deployment.md:23-41`).

`run-wiggles-supervised-v1.mjs:1-10` invokes the unchanged fail-closed factory before reading configuration, flags, input or keys. `live-executor-composition-v1.mjs:9-14` always rejects; it has no enable flag, test switch or signer dependency. The production validator cannot unlock it. Both that live factory and `mandate-v1.mjs` were also byte-compared to local HEAD and are unchanged.

## Additional essential regression gaps

Beyond the two blocker-specific regressions above, the following new-composition boundaries need direct coverage before promoting the candidate to a production source release:

1. **Partial signed-wire writes, file/directory fsync and close failures, plus episode-state commit failure after signed-intent registration.** Exercise the real runtime, verify no successful agent/channel response, preserve exact retained/ambiguous state and prohibit another signing attempt after reopen. Current new runtime retention faults target wire open and the second read (`wiggles-trusted-runtime-v1.test.mjs:28-37`), not each new-composition failure window. Reused unrelated filesystem durability tests do not exercise this adapter.
2. **Post-key-load revocation through the actual adapter.** Commit authenticated revocation after key IO but before its new pre-sign check; require zero signing and retained ambiguity. Existing concrete runtime coverage tests pre-delivery revocation and post-IO freshness expiry, while the reused control-plane race uses an injected signer.
3. **Lost result/output write.** Fail the result pipe after successful retention/registration and show ordinary restart preserves the same intent with no replacement signing. The existing channel tests cover framing, size, timeout and disabled CLI, not this output-failure scenario.

These are targeted coverage gaps, not additional demonstrated authorization bypasses. No new broad crash campaign, live disposal test or capture/rentEpoch redesign is asserted as performed or authorized here.
