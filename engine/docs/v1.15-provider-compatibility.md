## Pinned production request contract

Every item is exact and release-blocking:

- Fixed origin: `https://mainnet.helius-rpc.com/`; no caller-supplied URL or origin.
- Transport: JSON-RPC 2.0 POST; request id `wallet-acquisition-v2`.
- Authentication: API key in the fixed-origin `api-key` query parameter; presence only is checked by the operator and the value is never reported.
- Bulk method: `getTransactionsForAddress`.
- Address: the exact request wallet.
- `transactionDetails: "full"`.
- `commitment: "finalized"`; `processed` and `confirmed` are unsupported assumptions.
- `encoding: "json"`; `jsonParsed` is not accepted.
- `maxSupportedTransactionVersion: 0`; omission or support beyond v0 is a STOP condition.
- `tokenAccounts: "none"`. Scope is direct-wallet history only; associated-token-account expansion is deferred.
- `status: "any"`.
- `sortOrder: "desc"`.
- page size: 100.
- `minContextSlot` equals the finalized anchor slot.
- slot filter is `{ lte: anchor_slot }`; there is no server-side lower-time filter.
- First request omits `paginationToken`. Later requests preserve opaque pagination token bytes exactly. A terminal null token ends paging. Empty, oversized, unexpected, or repeated tokens fail closed.

The provider adapter validates every returned entry before canonical filtering. Every structurally valid entry consumes the enrichment transaction budget. Descending order, duplicate identity, conflicting duplicate bodies, page cap, entry cap, and terminal state are owned by Artifact orchestration rather than inferred from provider behavior.

## Completeness and fallback authority

Finalized standard-RPC `getSignaturesForAddress` is the sole completeness authority. It owns latest-state pagination, the finalized anchor, lower-bound proof, canonical source order, and latest-state recheck. Bulk full transactions are enrichment only and must reconcile exactly to that canonical set.

The only fallback is finalized `getTransaction` with parameters `[signature, { commitment: "finalized", encoding: "json", maxSupportedTransactionVersion: 0 }]`. It is missing-signature-only, runs in canonical source order, and has explicit allowance `0..8`. Contradictory, malformed, duplicate-conflicting, capped, timed-out, deadline-exhausted, or otherwise uncertain bulk evidence never becomes fallback-eligible. The planned JUP positive control pins allowance `0`.

## Response-shape assumptions

Reconfirm all of these before live operation:

- The Helius guide and example expose `blockTime`, `transaction`, and `meta` with the same transaction-information semantics used by `getTransaction`; the generated schema omits `blockTime` and `meta` from its required list. Artifact retains this inconsistency as a bounded provider-attested assumption, requires both fields, infers nothing when either is absent, null, or malformed, and emits no acquisition result on rejection.
- Transaction versions are only `legacy` or `0`.
- Static account keys are followed by loaded writable addresses and then loaded readonly addresses; every compiled program/account index resolves against that exact list. This order is established by the official Solana Versioned Transactions and RPC JSON Structures pages retrieved `2026-08-11`.
- `blockTime` is documented nullable, but Artifact requires a safe nonnegative value and fails closed on null.
- `meta` is required, including an explicit safe fee, aligned pre/post lamport vectors, token balance rows when applicable, loaded addresses for v0 messages, and inner instructions needed for supported reconciliation.
- Provider error prose, labels, descriptions, logs, URLs, headers, pagination data, and retry internals are non-authoritative and are not retained.
- Documented token-account historical coverage limitations do not expand direct-wallet scope. Any coverage/schema limitation that undermines reconciliation is a STOP condition.
