# Artifact v1.12 Operations

## Scope

This guide covers deterministic v1.12 closeout, package authority, read-only validation, and the boundary around the completed controlled RAY reproduction. It does not authorize acquisition, package publication, archive/economics mutation, deployment, upload, minting, signing, or Git release actions.

## Deterministic regression

Run the closeout runner directly from the repository root:

```text
node engine/src/run-v112-regression.mjs
```

Do not substitute an npm wrapper. The runner executes only checked-in deterministic suites. It includes the v1.9 and v1.10 regression runners, package contract/store/migration tests, package-first inventory and compatibility tests, package-native read/API tests, the ledger/candidate/promotion/verifier core, targeted orchestration, bounded acquisition mocks and retained real-provider-shape acceptance, and Share Card/public-demo checks.

The runner does not load credentials, call live Helius, run wallet-wide pipelines, write authoritative package/archive/economics roots, deploy, upload, mint, or sign. Temporary-directory store tests exercise write semantics only in isolated operating-system temporary roots.

## Authority and roots

Treat a validated `receipt_package_v1` as authoritative when an exact package exists for the receipt. Never manually join package members or trust a manifest without the complete package validator. Package-first readers must fail closed on malformed, conflicting, noncanonical, or cross-member-inconsistent package content.

The archive and economics roots remain compatibility inputs for legacy-only receipts. For a package-backed receipt, compatibility views are derived from validated package members. Do not repair a corrupt package by silently falling back to legacy projections.

Production package publication, if separately authorized, must use the documented filesystem-store API with an explicit pre-existing package root. Never copy member files directly, infer a default root, replace an existing receipt directory, or treat `commit_unknown` as permission for a blind retry. Follow `engine/docs/receipt-package-v1-operations.md` for stage, validation, commit, reconciliation, locking, and durability semantics.

## Golden identity checks

The focused package suites pin the JUP and RAY receipt hashes, package digests, and all five serialized member hashes. A closeout is valid only when these identities remain exact and the canonical verifier reports hash/schema/consistency validity, overall pass, and zero violations.

Any byte drift is a release blocker. Do not update golden values merely to make regression pass; first determine whether the change is a defect or an intentional new package/profile version.

## Controlled live evidence

The completed Slice 8B-RAY evidence is retained outside Git at:

```text
/root/artifact-recovery-evidence/live-probe-v112-ray
```

This is a host-local operational reference, not a repository dependency. It contains sanitized policies, summaries, digests, dry-run identities, logs, and checksums only. Do not copy it into Git, public-demo output, package members, archives, economics records, logs, or release assets. Do not expect the deterministic runner to access it.

The live result proved one exact RAY chain:

```text
bounded Helius page
  -> complete acquisition status
  -> two canonical normalized events
  -> retained-offline event equality
  -> Slice 7 dry-run
  -> published receipt hash
  -> pinned five-member package identity
```

That proof does not authorize another provider request or a new-wallet run. Every live acquisition requires separate explicit authorization and reviewed bounds.

## Operational provenance

Keep operational job provenance outside package identity. Request counts, provider status, retries, timeouts, cursor history, local evidence paths, source roots, process identity, staging names, runtime timestamps, recovery method, and administrative notes may appear in private sanitized job evidence, but never in package members or deterministic public bytes.

Never retain credentials, authenticated URLs, raw provider bodies, unrelated complete wallet history, private keys, or upload/mint/signing state in closeout evidence.

## Failure handling

Stop and investigate when any of these occurs:

- package/member digest drift;
- verifier failure or nonzero rule violations;
- package/legacy overlap conflict;
- corrupt package with a tempting legacy fallback;
- acquisition cap, timeout, retry exhaustion, malformed page, cursor anomaly, unsupported activity, or normalization ambiguity;
- `package_store_conflict`, `committed_package_invalid`, unreconciled `commit_unknown`, or held/stale lock; or
- mutation of package, archive, economics, public-demo, or tracked Git state during a read-only operation.

Hidden stages and locks are reader-invisible but require deliberate administrative review. Stale-stage cleanup is not automated in v1.12.

## Release closeout

Before proposing a release tag:

1. require `main`, a clean worktree baseline, and the intended source revision;
2. run `node engine/src/run-v112-regression.mjs` directly;
3. require every suite to pass with no live-network action;
4. review the release notes and limitations;
5. confirm no authoritative data root changed; and
6. leave commit, push, and tag creation to the Git owner.
