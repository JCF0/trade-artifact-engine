## Tested successor policy

Implemented in `engine/qualification/helius-provider/bounded-context-lag-v1.mjs`:

1. Only a correlated, screened HTTP-200 JSON-RPC envelope with explicit numeric
   error code **-32016**, a string error message, and a method from the fixed
   qualification read-method set is retry-eligible. Simulation is excluded.
   Submission methods are not in the permitted method set at all.
2. There are **at most two additional attempts across the entire session**, not
   two per method or per logical call. The first shared retry waits **250 ms**;
   the second waits **500 ms**. A further eligible refusal stops without dispatch.
3. Method and parameters are canonically snapshotted once per logical call.
   Every retry uses those same method/parameters, including the unchanged slot
   floor. Each physical attempt has a fresh correlated JSON-RPC ID; therefore
   complete request bytes differ in ID, not method or parameters.
4. Every original attempt and retry consumes the same **29-request ceiling**.
   Reservation is durable before transport. An uncertain reserved attempt remains
   consumed. A retry reservation is also durable and is never refunded if its
   following attempt becomes impossible. Restart cannot resume this evidence root
   as a fresh allowance: exclusive request/reservation names refuse reuse.
5. The effective monotonic cutoff is the smaller of the session limit and the
   launcher's **original absolute work deadline**, supplied in
   `/outer-deadline.json`. No retry, wait, successful response or logical call
   restarts it. Retention and unsigned construction also consume that interval.
6. Budget/deadline checks occur before retry reservation, after reservation,
   after waiting, and after attempt retention immediately before transport.
   If the remaining time cannot accommodate the bounded backoff, stop rather
   than sleep past the cutoff. The existing request timeout is tightened to
   remaining time. Late responses do not authorize another attempt.
7. Preserve **5,000 ms per request**, **60 s whole-launch**, the existing
   **50 s work / 55 s management** cutoffs, and existing byte limits:
   1,048,576 bytes per request/response; 16,777,216 aggregate response bytes.
8. Authentication failures, transport/screening ambiguity, malformed or
   uncorrelated envelopes, other RPC errors and simulation errors stop without
   retry. The unchanged accepted exchange uses one direct ClientRequest, no
   redirect handling, pooling or hidden transport retry. No submission transport
   or production scheduling policy is changed.
9. Success remains subject to the unchanged downstream account/context, exact
   owner-watermark, history, setup, static-fee/oracle, quote, fee and expiry gates.
   Retry success is not qualification success.

### Exact revised accounting

The predecessor's method maxima are preserved as **logical-call maxima** in this
version. `counts` measures all reserved physical attempts; `logical_counts`
measures new logical calls. The shared additional-attempt allowance can raise a
method's physical count above its logical maximum, but never the global ceiling.
This is why the old zero-retry specification must not be presented as governing
this successor.

| Method | Maximum logical calls |
|---|---:|
| getGenesisHash | 1 |
| getSlot | 1 |
| getBlock | 1 |
| getMultipleAccounts | 2 |
| getAccountInfo | 1 |
| getTokenAccountsByOwner | 2 |
| getSignaturesForAddress | 15 |
| getTransaction | 2 |
| getLatestBlockhash | 1 |
| getFeeForMessage | 1 |
| getBlockHeight | 1 |
| simulateTransaction | 1, never retried |

The sum of those maxima is **29**, not a guarantee that all can be used together
with retries. The invariant is **initial-attempt reservations + retry-attempt
reservations <= 29**, with **shared retry reservations <= 2**. It is not a
31-request plan. No history shortening or substituted response is used to force
completion when retries consume capacity needed by later steps.

Each attempt retains its original request, screened response if available,
reservation and completion. Records include physical ordinal, logical ordinal,
attempt ordinal, shared retry ordinal, canonical method/parameter template hash,
request/response identities, RPC disposition/code and elapsed time. Separate
`retry-N-reserved.json` records retain origin, delay, template identity and absolute
cutoff. The versioned closed ledger accounts for every attempt and retry reservation.
No response is fabricated for transport/authentication failures: fixture-generated
unsent or rejected bodies are synthetic-server test material, not admitted evidence.
