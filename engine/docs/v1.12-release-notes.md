# Artifact v1.12 Release Notes

Artifact v1.12 closes the receipt-package architecture and proves one bounded live-to-package reproduction without adding a production writer or hosted reconstruction service.

## Architectural problem corrected

Earlier proof and inventory surfaces depended on reduced archive and economics projections produced by separate local runs. Those projections remained useful compatibility records, but they were not one immutable object that independently bound the canonical receipt, verifier result, archive projection, economics projection, reconstruction profiles, and member bytes. Authority could therefore be split across several roots and readers could expose different provenance depending on which projection they reached.

V1.12 corrects that boundary with `receipt_package_v1`: one content-addressed, fully validated five-member package is authoritative for packaged receipts. Inventory, proof, verifier, board, Share Card, API, and public-demo readers can now derive their package-backed views from the same validated object.

## Authoritative package model

A package contains exactly:

- `manifest.json`
- `canonical-receipt.json`
- `verification.json`
- `archive-record.json`
- `economics.json`

The manifest binds the receipt hash, package digest, member hashes, and frozen reconstruction profiles. The validator requires canonical member bytes, exact cross-member identity, a fresh successful canonical verifier result, and zero rule violations. The Linux filesystem store stages all five members privately, validates readback, and publishes one complete receipt directory through an atomic no-clobber rename under an explicit pre-existing root.

Package identity excludes job and machine provenance. Provider URLs, credentials, raw history, recovery paths, local roots, process identity, staging names, runtime timestamps, retry history, upload state, mint state, and signing state are operational facts and never enter package members or `package_digest`.

## Package-first reads and legacy fallback

Package-first inventory resolves a receipt from a validated package when one exists. Archive/economics compatibility records are then derived from package members rather than independently trusted. A corrupt or conflicting package fails closed; it does not silently downgrade to legacy data.

Receipts without a package continue through the existing validated legacy archive path. This preserves read compatibility for the historical set while making authority explicit: packaged JUP/RAY receipts are package-authoritative, and the remaining 64 legacy receipts are archive-only.

## Targeted orchestration and bounded acquisition

`orchestrateTargetedReceiptPackageV1()` accepts complete normalized evidence, an explicit wallet/mint/type/segment target, frozen profiles, and an optional expected receipt hash. Dry-run builds and validates the complete package in memory without requiring or touching a package store. Commit mode remains a separate capability that requires an explicitly injected store.

The bounded Helius adapter adds a fail-closed acquisition contract with explicit historical bounds, page/transaction/attempt/time limits, strict page and cursor validation, deterministic target-scoped normalization, and typed sanitized errors. Caps, timeouts, malformed pages, cursor anomalies, retry exhaustion, unsupported target activity, and normalization ambiguity never become partial success.

One separately authorized controlled Helius run used one page and one HTTP request for the published RAY target. It proved `historical_bound_reached`, returned 100 transactions and exactly two normalized target events, and reported complete, non-truncated, non-capped, certain input.

Sanitized host-local evidence is retained operationally at `/root/artifact-recovery-evidence/live-probe-v112-ray`. It is private operational evidence, is not copied into Git, and is not an input to deterministic regression.

## Package-native public-byte compatibility

For the authoritative JUP/RAY packages, package-derived compatibility records and package-native proof, verifier, board, Share Card, API, and public-demo projections preserve the pinned deterministic public behavior. Package provenance is surfaced where appropriate without adding provider/job/private-path data to public bytes. Legacy-only receipts retain their existing validated archive behavior.

## Security and capability boundaries

V1.12 keeps acquisition, deterministic construction, storage, reading, public projection, upload, minting, and signing as separate capabilities:

- the provider-neutral acquisition contract imports no network or filesystem capability;
- the Helius adapter receives its HTTP and credential capabilities explicitly and sanitizes failures;
- dry-run orchestration receives no package store and cannot publish;
- the filesystem store has no default production root and performs no acquisition or network action;
- package readers validate before projection and fail closed on conflicts or corruption;
- the deterministic v1.12 regression runner contains no live Helius call and performs no deployment, upload, mint, or signing action; and
- the existing devnet mint pipeline remains separate from package closeout.
